6. Mapping Course ​

6.1 Introduction to URDF Models ​

6.1.1 URDF Overview ​

URDF stands for Unified Robot Description Format and is an XML-based format used to describe a robot's structure, dimensions, mass, coordinate-frame relationships, and motion constraints.

A robot model generally consists of multiple links and joints:

  • Link: Represents a rigid component such as the chassis, a bracket, robotic arm, or wheel. A link can include visual, collision, and inertial properties.

  • Joint: Connects a parent link to a child link and defines their relative position, orientation, type of motion, and motion limits.

When links are connected by joints, they form a tree-structured kinematic model. A URDF file records the hierarchy between components and describes their geometry, materials, inertia, and collision properties. RViz, Gazebo, and robot-control nodes in ROS 2 can read and use this information.

A minimal URDF file has the following structure:

xml
<?xml version="1.0"?>
<robot name="robot_name">
  <link name="base_link"/>
  <joint name="base_joint" type="fixed">
    <parent link="base_link"/>
    <child link="body_link"/>
  </joint>
  <link name="body_link"/>
</robot>

robot is the root element of the model. Every link and joint must be defined inside it.

6.1.2 URDF and Xacro Compared ​

URDF is straightforward and easy to understand, making it suitable for robots with relatively simple structures. As a robot becomes more complex, however, a URDF file often develops repeated code, excessive length, and parameters that are difficult to maintain consistently.

Xacro is an XML macro language that extends URDF. A Xacro file is ultimately expanded into URDF, but it supports variables, mathematical expressions, conditions, and macros to reduce duplication and improve reuse. For example, because the left and right legs of a humanoid robot are usually similar, one leg can be defined as a macro and instantiated twice with different parameters.

ComparisonURDFXacro
File typeDirect robot-model descriptionXML macro file used to generate URDF
Code reuseSimilar structures must be repeatedVariables, macros, and parameters can be reused
ReadabilityDirect and suitable for learning or debuggingBetter for complex models, but requires knowledge of Xacro syntax
Typical useSimple robots or inspection of the generated modelComplex robots and model families with multiple variants

URDF is therefore better suited to learning model structure and inspecting the generated result, while Xacro is better suited to authoring and maintaining complex robot models.

6.1.3 Basic URDF Syntax ​

URDF uses XML syntax. Reading or writing a URDF file requires an understanding of XML elements, attributes, and comments, as well as common URDF tags such as link, joint, and robot.

  • Basic XML Structure

1. Elements

An element consists of an opening tag and a closing tag and represents a structural block:

xml
<element>
</element>

An element with no child content can use the self-closing form:

xml
<element/>

2. Attributes

Attributes appear in the opening tag and define values such as a name, dimensions, or position:

xml
<element attribute_1="value_1" attribute_2="value_2">
</element>

3. Comments

Comments are ignored during model parsing and can be used to document the code:

xml
<!-- Comment -->

4. Links: link

A link represents a rigid robot component. The link tag requires only a unique name attribute. Add visual, collision, and inertial elements as required by the application:

xml
<link name="base_link">
  <visual>...</visual>
  <collision>...</collision>
  <inertial>...</inertial>
</link>

The code above illustrates the structure only. The omitted content prevents it from being used as a complete model. For visualization in RViz, define visual. Add collision when collision detection is required, and add inertial with accurate component data for physics simulation.

TagDescription
visualDefines the model's appearance in RViz, Gazebo, and similar tools.
collisionDefines the geometry used for collision detection.
inertialDefines mass, center of mass, and the inertia matrix for physics simulation.
originDefines relative position and orientation. xyz specifies position, and rpy specifies rotations about the X, Y, and Z axes.
geometryDefines a geometric shape using box, cylinder, sphere, or mesh.
materialDefines the visual material. The rgba value of color sets color and opacity.
massDefines link mass in kilograms.
inertiaDefines the inertia matrix using attributes such as ixx, ixy, ixz, iyy, iyz, and izz.

NOTE

rpy represents roll about the X-axis, pitch about the Y-axis, and yaw about the Z-axis, in radians. The inertia matrix describes an object's resistance to changes in rotational motion and is normally obtained from 3D modeling software or a calculation tool.

5. Joints: joint

A joint connects a parent link to a child link and defines how the child can move relative to the parent. parent, child, and origin describe the connection. Whether axis, limit, and dynamics are required depends on the joint type:

xml
<joint name="joint_name" type="joint_type">
  <parent link="parent_link"/>
  <child link="child_link"/>
  <origin xyz="0 0 0" rpy="0 0 0"/>
</joint>
Joint typeDescription
continuousRotates continuously about one axis. Commonly used for wheels.
revoluteRotates about one axis within specified angular limits.
prismaticTranslates along a specified axis within a defined range.
planarTranslates and rotates within a plane.
floatingSupports six degrees of freedom in translation and rotation.
fixedAllows no relative motion. Commonly used for fixed sensors and brackets.
TagDescription
parentSpecifies the parent link.
childSpecifies the child link.
originSpecifies the joint frame's position and orientation relative to the parent-link frame.
axisSpecifies the axis of rotation or translation.
limitLimits the joint's range of motion, maximum effort, and maximum velocity.
dynamicsDefines dynamic properties such as damping and friction.
mimicMakes the joint follow the motion of another joint.
safety_controllerDefines joint safety-control parameters.

Typical parameter requirements for movable joints are listed below:

Joint typeaxislimitUnits and notes
continuousNormally specifiedOptional. Do not set finite lower and upper limitsRotates continuously about the specified axis. Set effort and velocity if required.
revoluteNormally specifiedRequires lower, upper, effort, and velocitylower and upper are in radians.
prismaticNormally specifiedRequires lower, upper, effort, and velocitylower and upper are in meters.
planarNormally set to the plane normalNormally unusedThe child link can move within the specified plane.
floatingUnusedUnusedThe child link has six degrees of freedom.
fixedUnusedUnusedNo relative motion exists between the parent and child links.

The following examples define a revolute joint and a prismatic joint:

xml
<joint name="hinge_joint" type="revolute">
  <parent link="parent_link"/>
  <child link="child_link"/>
  <origin xyz="0 0 0" rpy="0 0 0"/>
  <axis xyz="0 0 1"/>
  <limit lower="-1.57" upper="1.57" effort="10" velocity="1"/>
</joint>

<joint name="slide_joint" type="prismatic">
  <parent link="parent_link"/>
  <child link="slider_link"/>
  <origin xyz="0 0 0" rpy="0 0 0"/>
  <axis xyz="0 0 1"/>
  <limit lower="0" upper="0.20" effort="10" velocity="0.10"/>
</joint>

For a revolute joint, lower and upper define the angular range in radians. For a prismatic joint, they define the linear travel in meters. A continuous joint can specify axis but does not use finite lower and upper position limits. A fixed joint does not require axis, limit, or dynamics.

6. The robot Tag

robot is the root tag in a URDF file. All link, joint, and related extension tags must be contained within it:

xml
<robot name="robot_name">
  <!-- Define links and joints here -->
</robot>

7. The gazebo Tag

The gazebo tag adds simulator-specific settings such as materials, friction coefficients, sensors, and plugins. It does not change the underlying URDF link-and-joint structure, but it affects the model's appearance and physical behavior in Gazebo.

6.1.4 Creating a Simple URDF Model ​

This section builds a simple model consisting of a cylindrical base and a rectangular body to demonstrate how robot, link, and joint form a complete URDF file. The model contains the root link base_link and the child link body_link, connected by a fixed joint.

Create a file named simple_robot.urdf. URDF uses meters for length, with m as the unit symbol. It uses kilograms for mass, with kg as the unit symbol. Angles are expressed in radians, with rad as the unit symbol.

  • Set the Robot Model Name

A URDF file begins with an XML declaration and the root robot tag. The name attribute identifies the robot model, and every link and joint must be defined within this tag.

xml
<?xml version="1.0"?>
<robot name="simple_robot">
  <!-- Define links and joints here -->
</robot>

A URDF file can contain only one root robot tag. Use a unique, descriptive name, such as simple_robot in this example.

  • Define the Links

Links represent rigid robot components. Every link must have a unique name. In this example, base_link is the root link and body_link represents the body mounted above the base.

A link commonly contains the following elements:

  • visual: Defines the appearance shown in RViz, Gazebo, and similar tools.

  • collision: Defines the geometry used for collision detection. A basic model can reuse the visual geometry, while a production model commonly uses a simpler collision shape.

  • inertial: Defines mass, center of mass, and the inertia matrix. Include it for physics simulation.

Within visual and collision, geometry specifies the shape. This example uses cylinder for the base, where radius specifies its radius and length specifies its length along the Z-axis. It uses box for the body, where the three size values specify its X, Y, and Z dimensions. origin sets the element's position and orientation relative to its link frame.

xml
<link name="base_link">
  <visual>
    <geometry>
      <cylinder radius="0.15" length="0.04"/>
    </geometry>
    <material name="blue">
      <color rgba="0.15 0.45 0.85 1"/>
    </material>
  </visual>
  <collision>
    <geometry>
      <cylinder radius="0.15" length="0.04"/>
    </geometry>
  </collision>
  <inertial>
    <mass value="1.0"/>
    <inertia ixx="0.0058" ixy="0" ixz="0" iyy="0.0058" iyz="0" izz="0.0113"/>
  </inertial>
</link>

The body's local coordinate frame is located at the center of its bottom face. The origin of its visual, collision, and inertial elements is therefore shifted upward by 0.05 m along the Z-axis, placing the box center above the link frame.

xml
<link name="body_link">
  <visual>
    <origin xyz="0 0 0.05" rpy="0 0 0"/>
    <geometry>
      <box size="0.20 0.12 0.10"/>
    </geometry>
    <material name="yellow">
      <color rgba="0.95 0.65 0.10 1"/>
    </material>
  </visual>
  <collision>
    <origin xyz="0 0 0.05" rpy="0 0 0"/>
    <geometry>
      <box size="0.20 0.12 0.10"/>
    </geometry>
  </collision>
  <inertial>
    <origin xyz="0 0 0.05" rpy="0 0 0"/>
    <mass value="0.5"/>
    <inertia ixx="0.0010" ixy="0" ixz="0" iyy="0.0021" iyz="0" izz="0.0023"/>
  </inertial>
</link>

NOTE

The example mass and inertia values are approximations for uniform solids and are suitable for learning and basic visualization. For physics simulation or real-world control, replace them with the actual component mass, center of mass, and inertia values.

  • Define the Joint

A joint defines the coordinate relationship and permitted motion between a parent link and a child link. Because the body is fixed to the base in this example, the joint type is fixed. A fixed joint allows no relative motion and does not require axis, limit, or dynamics.

xml
<joint name="base_to_body" type="fixed">
  <parent link="base_link"/>
  <child link="body_link"/>
  <origin xyz="0 0 0.02" rpy="0 0 0"/>
</joint>

parent specifies the reference link, and child specifies the connected child link. Here, origin places the joint frame 0.02 m above the base_link frame along the positive Z-axis, at the center of the cylinder's top surface. Because the geometry of body_link is shifted another 0.05 m upward relative to its own frame, the bottom face of the body aligns with the joint position.

For a movable component, configure the joint as described in 6.1.3 Basic URDF Syntax. Specify axis for a continuous joint. Specify axis and angular limit values for a revolute joint. Specify axis and linear travel limits for a prismatic joint. A fixed joint does not require these motion parameters.

  • Assemble and Validate the Model

After placing both links and the fixed joint inside the same robot tag, the complete simple_robot.urdf file is as follows:

xml
<?xml version="1.0"?>
<robot name="simple_robot">
  <link name="base_link">
    <visual>
      <geometry>
        <cylinder radius="0.15" length="0.04"/>
      </geometry>
      <material name="blue">
        <color rgba="0.15 0.45 0.85 1"/>
      </material>
    </visual>
    <collision>
      <geometry>
        <cylinder radius="0.15" length="0.04"/>
      </geometry>
    </collision>
    <inertial>
      <mass value="1.0"/>
      <inertia ixx="0.0058" ixy="0" ixz="0" iyy="0.0058" iyz="0" izz="0.0113"/>
    </inertial>
  </link>

  <link name="body_link">
    <visual>
      <origin xyz="0 0 0.05" rpy="0 0 0"/>
      <geometry>
        <box size="0.20 0.12 0.10"/>
      </geometry>
      <material name="yellow">
        <color rgba="0.95 0.65 0.10 1"/>
      </material>
    </visual>
    <collision>
      <origin xyz="0 0 0.05" rpy="0 0 0"/>
      <geometry>
        <box size="0.20 0.12 0.10"/>
      </geometry>
    </collision>
    <inertial>
      <origin xyz="0 0 0.05" rpy="0 0 0"/>
      <mass value="0.5"/>
      <inertia ixx="0.0010" ixy="0" ixz="0" iyy="0.0021" iyz="0" izz="0.0023"/>
    </inertial>
  </link>

  <joint name="base_to_body" type="fixed">
    <parent link="base_link"/>
    <child link="body_link"/>
    <origin xyz="0 0 0.02" rpy="0 0 0"/>
  </joint>
</robot>

If the URDF validation tool is installed, run the following command from the file's directory to check the XML and link-tree structure:

bash
check_urdf simple_robot.urdf

After validation succeeds, the model should have one root link, base_link, with body_link connected through the fixed joint base_to_body. If validation fails, check that every tag is closed correctly, all link and joint names are unique, and every parent and child link referenced by a joint has been defined.

6.2.3 Overview of the Robot Body Model ​

Using the actual clawpi.xacro and mecanum.xacro files, this section explains how the robot body model is assembled from multiple Xacro files, links, joints, and mesh models. The Xacro files are expanded into URDF for use by RViz, Gazebo, and robot-control nodes.

  • Model Entry Point and Included Files

Open the robot model's entry file from the urdf directory:

bash
vim clawpi.xacro

The contents of clawpi.xacro are shown below:

xml
<?xml version="1.0" encoding="utf-8"?>
<robot name="clawpi" xmlns:xacro="http://ros.org/wiki/xacro">
  <xacro:include filename="mecanum.xacro"/>
  <xacro:include filename="inertial_matrix.xacro"/>
</robot>

  • robot name="clawpi" defines the robot model name, and clawpi.xacro serves as the model entry point.

  • xmlns:xacro declares the Xacro namespace, enabling extension tags such as xacro:include and xacro:macro.

  • The two xacro:include elements include mecanum.xacro and inertial_matrix.xacro.

  • mecanum.xacro primarily defines the body links, joints, and mesh models. Review the actual inertial_matrix.xacro file for its internal definitions.

clawpi.xacro therefore organizes the component files, while most of the robot body structure is defined in mecanum.xacro. Every included file must exist at the specified path when Xacro is expanded. Otherwise, a file-not-found error occurs.

  • Basic mecanum.xacro Structure and Coordinate Convention

Open the main body model file:

bash
vim mecanum.xacro

The key declarations at the beginning of the file are shown below:

xml
<?xml version="1.0"?>
<robot name="mecanum" xmlns:xacro="http://ros.org/wiki/xacro">
  <!--
    Model exported from SolidWorks.
    Coordinate convention: +X front, +Y left, +Z up, right-handed.
  -->

The model was exported from SolidWorks and uses a right-handed coordinate system: +X points forward, +Y points left, and +Z points upward. Interpret all subsequent origin xyz values, joint positions, and joint-axis directions according to this convention.

The file defines a reusable material named solidworks_body:

xml
<material name="solidworks_body">
  <color rgba="0.792156862745098 0.819607843137255 0.933333333333333 1"/>
</material>

Multiple visual elements can reuse this material. The four rgba values represent red, green, blue, and alpha, respectively.

  • Chassis Reference and Body Link

In the two source files provided, base_footprint has no parent joint and is therefore the root link of the model tree. It is connected to base_link by a fixed joint:

xml
<link name="base_footprint"/>

<joint name="base_footprint_to_base_link" type="fixed">
  <parent link="base_footprint"/>
  <child link="base_link"/>
  <origin xyz="0 0 0.048" rpy="0 0 0"/>
</joint>

base_footprint serves as the robot's reference link on the horizontal plane, while base_link is the main body frame. The joint origin places base_link 0.048 m above base_footprint along the Z-axis. The two Xacro files shown here do not define odom. The transform from odom to the robot base is normally published by the odometry or chassis driver node.

base_link is the main robot-body link and includes inertial, visual, and collision properties:

xml
<link name="base_link">
  <inertial>
    <origin xyz="-0.0111741784726399 -0.00938133906168431 0.00222304260879017" rpy="0 0 0"/>
    <mass value="0.257918255798669"/>
    <inertia
      ixx="0.00015526546745493"
      ixy="5.55225972274923E-08"
      ixz="5.87872490508866E-06"
      iyy="0.000317158526917481"
      iyz="2.82843759137074E-08"
      izz="0.000427369935552488"/>
  </inertial>
  <visual name="base_link_visual">
    <geometry>
      <mesh filename="package://clawpi_description/meshes/base_link.STL"/>
    </geometry>
    <material name="solidworks_body"/>
  </visual>
  <collision name="base_link_collision">
    <geometry>
      <mesh filename="package://clawpi_description/meshes/base_link.STL"/>
    </geometry>
  </collision>
</link>

  • inertial defines the body's mass, center of mass, and inertia matrix for physics simulation.

  • visual uses base_link.STL to define the displayed appearance.

  • collision uses the same mesh for collision detection.

  • package://clawpi_description/meshes/ tells ROS 2 to locate the mesh in the clawpi_description package.

  • Pan-and-Tilt Links and Revolute Joints

The pan-and-tilt assembly consists of gimbal_yaw_link and gimbal_pitch_link, connected to the robot body through joint2 and joint1, respectively.

The yaw joint, joint2, is defined as follows:

xml
<joint name="joint2" type="revolute">
  <parent link="base_link"/>
  <child link="gimbal_yaw_link"/>
  <origin xyz="0.037211992 0 0.047739788" rpy="0 0 0"/>
  <axis xyz="0 0 1"/>
  <limit lower="-1.570796327" upper="1.570796327" effort="1.0" velocity="2.0"/>
</joint>

The parent of joint2 is base_link, and its child is gimbal_yaw_link. It rotates about the Z-axis over an angular range of approximately -pi/2 to pi/2.

The pitch joint, joint1, is defined as follows:

xml
<joint name="joint1" type="revolute">
  <parent link="gimbal_yaw_link"/>
  <child link="gimbal_pitch_link"/>
  <origin xyz="0.010537478 0 0.013335579" rpy="0 0 0"/>
  <axis xyz="0 -1 0"/>
  <limit lower="-1.570796327" upper="1.570796327" effort="1.0" velocity="2.0"/>
</joint>

The parent of joint1 is gimbal_yaw_link, and its child is gimbal_pitch_link. It rotates about the negative Y-axis. Both joints are revolute joints: axis specifies the rotation axis, while limit defines the angular range, maximum effort, and maximum velocity.

  • Mecanum Wheel Macro

The file uses xacro:macro to encapsulate the repeated structure of all four wheels in a single macro:

xml
<xacro:macro name="mecanum_wheel" params="link_name joint_name mesh_name cover_mesh_name x y z">
  <link name="${link_name}">
    <visual name="${link_name}_visual">
      <geometry>
        <mesh filename="package://clawpi_description/meshes/${mesh_name}"/>
      </geometry>
      <material name="solidworks_body"/>
    </visual>
    <collision name="${link_name}_collision">
      <geometry>
        <mesh filename="package://clawpi_description/meshes/${mesh_name}"/>
      </geometry>
    </collision>
  </link>
  <joint name="${joint_name}" type="continuous">
    <parent link="base_link"/>
    <child link="${link_name}"/>
    <origin xyz="${x} ${y} ${z}" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>
  </joint>
  <link name="${link_name}_hub_cover_Link">
    <visual name="${link_name}_hub_cover_visual">
      <geometry>
        <mesh filename="package://clawpi_description/meshes/${cover_mesh_name}"/>
      </geometry>
      <material name="solidworks_body"/>
    </visual>
    <collision name="${link_name}_hub_cover_collision">
      <geometry>
        <mesh filename="package://clawpi_description/meshes/${cover_mesh_name}"/>
      </geometry>
    </collision>
  </link>
  <joint name="${joint_name}_hub_cover_fixed" type="fixed">
    <parent link="${link_name}"/>
    <child link="${link_name}_hub_cover_Link"/>
    <origin xyz="0 0 0" rpy="0 0 0"/>
  </joint>
</xacro:macro>

The macro parameters are described below:

ParameterDescription
link_nameWheel link name.
joint_nameWheel rotation-joint name.
mesh_nameWheel STL mesh filename.
cover_mesh_nameHub-cover STL mesh filename.
x, y, zWheel-joint position relative to base_link.

The macro is instantiated four times to generate the four wheel assemblies:

xml

6.3 SLAM Mapping Principles ​

6.3.1 Introduction to SLAM ​

To reach a destination, a person must know their current position, whether or not a map is available. People perceive their surroundings with their eyes. ClawPi uses LiDAR. SLAM stands for Simultaneous Localization and Mapping.

Localization estimates the robot's pose in a coordinate frame. The reference frame may be established from the first keyframe, an existing global map, landmarks, or GPS data.

Mapping creates a representation of the robot's surroundings from sensor observations. The basic geometric elements of the map are points. The resulting map supports localization and navigation. Navigation includes global and local path planning, followed by motion control that drives the robot along the planned route.

6.3.2 How SLAM Builds a Map ​

SLAM mapping consists of three main stages:

1. Preprocessing: Optimize the raw LiDAR point-cloud data by removing problematic measurements or applying filtering.

The LiDAR emits laser pulses that strike surrounding objects and scatter.

Some of the light returns to the LiDAR receiver. The sensor uses the reflected signal to calculate the distance from the LiDAR to each measured point.

A point cloud is the collection of environmental measurements acquired by the LiDAR. Each point contains an angle and distance and represents part of the surroundings visible to the sensor.

2. Matching: Match the current local point-cloud data to the corresponding location on the existing map.

A LiDAR SLAM system normally compares scans acquired at different times to estimate the sensor's relative translation and rotation, thereby updating the robot's pose.

3. Map Integration: Add the latest LiDAR data to the existing map to complete the map update.

6.3.3 Mapping Guidelines ​

1. When mapping begins, position the robot facing a straight wall or a closed cardboard box so that the LiDAR can detect as many points as possible.

2. For every route the robot may travel, scan the full 360° surroundings with the LiDAR to improve map completeness.

3. In a large environment, first complete a mapping loop to establish loop closure, then scan smaller environmental details.

6.3.4 Evaluating the Map ​

After mapping is complete, use the following criteria to determine whether the map is suitable for navigation:

1. Check whether obstacle boundaries are clear.

2. Check whether any areas of the map are inconsistent with the actual environment, such as areas affected by incomplete loop closure.

3. Check for gray, unmapped areas within the robot's operating area.

4. Check for temporary obstacles, such as moving objects, that will not be present during later localization.

5. Confirm that the surroundings have been mapped through 360° from every location in the robot's operating area.

6.4 slam_toolbox Mapping Algorithm ​

6.4.1 Algorithm Overview ​

SLAM Toolbox combines laser-range data provided as LaserScan messages and uses the TF transform from odom to base to create a two-dimensional map. It supports complete serialization and reloading of SLAM map data and pose graphs for continued mapping, localization, map merging, and other operations. SLAM Toolbox can run in synchronous mode, which processes all valid sensor measurements even when they are delayed, or asynchronous mode, which processes valid measurements when possible.

SLAM Toolbox provides a full-featured SLAM solution that can replace ROS packages such as gmapping, cartographer, karto, and hector. It is built on the scan matcher from the Karto core, which has been widely used and optimized for this package. It also introduces an optimization plugin based on Google Ceres and a localization method called elastic pose-graph localization. This method adds a sliding window of measurements to the graph for optimization and refinement. Changed local features can be tracked instead of being treated as deviations. When the robot leaves an area, redundant nodes are removed without affecting the long-term map.

slam_toolbox provides the following 2D SLAM capabilities:

  • Build maps and save PGM files

  • Refine, rebuild, or continue mapping from a saved map

  • Continue long-term mapping and remove irrelevant data from new LiDAR scans

  • Optimize localization on an existing map or use LiDAR odometry without mapping

  • Support synchronous and asynchronous mapping

  • Merge maps dynamically

  • Use plugin-based optimization solvers, including Google Ceres

  • Provide an interactive RViz plugin

  • Provide RViz tools for manipulating nodes and connections during mapping

  • Serialize maps and store data without loss

KARTO：

Karto SLAM is based on graph optimization and uses highly optimized, non-iterative Cholesky decomposition to solve sparse systems. The map is represented as a graph in which each node corresponds to a point on the robot trajectory and an associated set of sensor measurements. The graph is updated whenever a new node is added.

The ROS version of Karto SLAM uses Sparse Pose Adjustment, or SPA, together with scan matching and loop-closure detection. Memory requirements increase as the number of landmarks grows. However, graph optimization has an advantage in large environments because the graph contains only robot pose nodes. The map is generated after the poses have been estimated.

6.5 Troubleshooting ​

Q1: The URDF Model Fails to Load

Possible causes: The model file path is incorrect, the XML contains a syntax error, or a required package is missing.

Solutions:

1. Check that the URDF file path is correct.

2. Run check_urdf to validate the model syntax.

3. Confirm that all required mesh files exist.

Q2: The Map Contains Duplicated or Ghosted Features

Possible causes: The robot is moving too quickly, the IMU is not calibrated, or odometry error has accumulated.

Solutions:

1. Reduce the robot's speed. When using keyboard control, tap the W key briefly.

2. Calibrate the IMU as described in 3. Motion Control / 3.2.1 IMU Calibration.

3. Maintain a steady speed and avoid sudden turns while mapping.

Q3: The Map-Saving Command Fails

Possible causes: The destination path does not exist, the map_saver tool is not installed, or a command argument is incorrect.

Solutions:

1. Confirm that the terminal is in the correct map save directory.

2. Check that the map_saver_cli command is available.

3. Confirm that the filename argument is formatted correctly, such as -f "map_01".

Q4: The Robot Position Is Displayed Incorrectly After Mapping

Possible causes: The initial pose has not been set, or AMCL localization has not started.

Solutions:

1. Use 2D Pose Estimate in RViz to set the robot's initial pose.

2. Confirm that the AMCL localization node is running.

3. Check that the TF transforms are operating normally.

Q5: WinSCP Cannot Connect to the Robot

Possible causes: The IP address is incorrect, the SSH service is disabled, or the network connection is unavailable.

Solutions:

1. Confirm that the computer and robot are on the same local network.

2. Use ping to test network connectivity.

3. Confirm that SSH is enabled on the Raspberry Pi. The default port is 22.
